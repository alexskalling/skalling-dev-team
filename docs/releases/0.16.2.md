# 0.16.2 — commits autónomos con trabajo ajeno en la carpeta

El reporte de betterhealth mostró tres fallas: confundir cambios previos con
scope creep; exigir que todo el índice perteneciera a un único workflow; y
prohibir revisar el runtime de Skalling que el mismo hook exigía revisar.
Alex además indicó ejecutar el helper humano y mezclar tooling con producto.
Ese diagnóstico no era una solución válida.

## Comportamiento

- `skalling_workflow commit` recibe id y mensaje. Solo Teo/Jhon/Luz pueden usarlo,
  con el candidato y la cobertura ya verificados según riesgo. No hace push.
- El motor construye un índice temporal, sella ese diff, corre Git con sus hooks
  y conserva las entradas ajenas del índice original, incluso staging parcial.
  Devuelve el SHA; no necesita que el usuario ejecute un comando después.
- La carpeta de trabajo conserva cambios de otras tareas. El workflow captura
  su identidad al comenzar y detecta modificaciones posteriores. Para flujos
  antiguos, Alex puede declarar procedencia con `preserve_external`: no puede
  excluir archivos de su propio alcance ni inferir que todo lo ajeno es seguro.
- El bundle de runtime se admite como archivos enumerados en una unidad high
  con Jhon y Luz. `.opencode/context`, bases privadas y secretos permanecen
  fuera del alcance. No se agrega el bundle entero al commit de una feature.
- Fallos de hooks siguen bloqueando; no se desactivan ni se fabrican receipts.
  Otra operación con index.lock bloquea el commit sin borrar su lock.

## Verificación y límites

Las regresiones reproducen RED antes del cambio y crean commits reales con el
hook de Git activo: staging de tooling ajeno, contenido staged distinto del
working tree, trabajo previo del usuario, primer commit, reintento sin duplicar,
rechazo de un hook y lock de otro proceso. Se prueban los tres roles.
Resultados: motor 72/72; plugin 10/10; guard y paridad correctos; coherencia de
versión 11/11. OpenCode nativo confirma permisos de commit local de los tres
roles y mantiene push/amend sujetos a permiso. Esa prueba termina antes de
inferencia: no se presenta como una evaluación autónoma del modelo.
Las comprobaciones funcionales siguen correspondiendo a la unidad declarada:
separar Git no demuestra por sí solo independencia lógica entre cambios.
No se alteró ni se certificó el fix SEO de betterhealth.

El rollback es revertir motor, helper, protocolo de agentes y pruebas de esta
unidad. La migración 060 solo actualiza la versión; no elimina datos. Los
workflows existentes conservan su evidencia, sin convertirlos en éxitos.
